# ADR 0025 — Expire action approvals atomically and document 024/025 locks and exit paths

## Context

In migration 003, `public.expire_approval_request(uuid)` marked `approval_requests.status = 'expired'` and wrote `approval.expired` to `audit_log`, leaving the subject row untouched. For drafts (`subject_type = 'draft'`), `drafts_one_live_idx` scopes uniqueness per `in_reply_to_message_id`, so an uncancelled draft only blocks that single message. For actions (`subject_type = 'action'`), leaving `actions.status = 'pending_approval'` left `actions_one_live_order_money` (added in migration 024) permanently satisfied on `(tenant_id, input->>'order_number')`, locking future messages for that order out of proposing a refund.

Separately, migration 024 requires order-scoped `money` actions to match current `order_refund_eligibility` evidence (`amount`, `currency`, `eligible = true`). While the database trigger already rejected edited amounts via `CHECK` violation, `POST /approvals/{id}/decide` was not yet exposed in the core API to handle reviewer decisions cleanly and return an explicit `409 Conflict` for refund amount edits.

## Decision

1. **Cancel pending/proposed action subjects on approval expiry (migration 025).**
   `public.expire_approval_request(p_request_id uuid)` keeps draft expiry semantics untouched, and when `req.subject_type = 'action'` now atomically transitions the matching `public.actions` row (`(tenant_id, case_id, id, payload_hash)` with `status IN ('proposed', 'pending_approval')`) to `'cancelled'` and appends an `action.cancelled` entry to `public.audit_log` with `details = {"reason": "approval_expired", "approval_request_id": <id>}` in the same database transaction.
2. **Expose `POST /approvals/{id}/decide` with credential binding and `409` edit refusal.**
   Added `services/core/app/api/approvals.py` backed by `SWITCHBOARD_APPROVAL_CREDENTIALS` (`tenant_id`, `reviewer_id`, `channel`, `token`). When `record_approval_decision` rejects an `"edited"` decision on an order-scoped `money` action because the edited amount or currency diverges from eligibility evidence, the endpoint rolls back and returns `409 Conflict` (`"Order refund amount cannot be edited; amount is fixed by eligibility evidence"`), leaving the original action `pending_approval` and approval request `pending`.

## Locks and Limits Added in Migrations 024 and 025 (Exit Conditions)

### Transactional Locks (024)

| Lock / Limit | Scope & Purpose | Blocked State | How It Exits |
|---|---|---|---|
| `public.lock_order_evidence(tenant_id, order_number)` | Transaction-scoped advisory lock (`pg_advisory_xact_lock`) serializing refund proposals and eligibility checks per `(tenant, order_number)` | Concurrent callers wait up to `lock_timeout` (`3000ms`) and `statement_timeout` (`5000ms`) | Automatic release on `COMMIT` or `ROLLBACK` (or lock/statement timeout) |
| `FOR UPDATE` / `FOR SHARE` row locks | Locks on `cases`, `actions`, `approval_requests`, `demo.shop_orders`, `tenants`, `tenant_packs`, `pack_tools`, `tools` across eligibility/proposal/claim/consume/complete/reconcile/expiry | Concurrent writers/reviewers serialize on the row | Automatic release on `COMMIT` or `ROLLBACK` |

### Uniqueness & Replay Limits (024 & 025)

| Lock / Limit | Scope & Purpose | Blocked State | How It Exits |
|---|---|---|---|
| `actions_one_live_order_money` (024) | Partial unique index on `(tenant_id, (input->>'order_number')) WHERE risk_level = 'money' AND input ? 'order_number' AND status NOT IN ('rejected','cancelled','failed')` | Any second refund proposal for the order receives `{"waiting": "order_refund_already_exists"}` (or unique violation in SQL) | A reviewer uses `POST /approvals/slack` or `POST /approvals/{id}/decide` to reject or replace a pending refund. Rejection releases the order. Replacement keeps it reserved for the successor. `wf_sla_watchdog` calls `POST /actions/approvals/expire` for unanswered requests and `POST /actions/approvals/expire-unclaimed` for approved actions that miss the claim window. Either cancellation releases the order. A worker calls `POST /actions/{id}/claim` and `/complete` to execute, or `wf_action_reconciler` calls `/reconcile` after the lease. Confirmed failure releases the order. An inconclusive lookup holds it for operator reconciliation. Execution reserves the order permanently. See [ADR 0026](0026-every-live-state-has-an-exit.md). |
| `demo.order_refunds` unique constraint (024) | `UNIQUE (tenant_id, order_number)` and `demo.shop_orders.status = 'refunded'` / `refunded_at` | Duplicate mock payout for the same order fails closed in `demo.issue_order_refund` | **Permanent** for the refunded order; eligibility checks report `already_refunded` for subsequent inquiries. |
| `demo.refund_eligibility` unique constraint (024) | `UNIQUE (tenant_id, action_id)` | Re-running mock eligibility with the same `action_id` cannot duplicate receipts | One receipt per lookup `action_id`; fresh messages create new lookup actions. |

### Validation, Approval & Execution Gates (024 & 025)

| Lock / Limit | Scope & Purpose | Blocked State | How It Exits |
|---|---|---|---|
| `refund` config & tool availability (`refunds.py`) | Requires active `tenant_packs` with `refund` config and `order_refund_issue` `mock` tool in `pack_tools` | Returns `{"waiting": "refund_not_configured"}` or `{"waiting": "refund_tool_unavailable"}` | The tenant configuration operator enables and pins a pack with valid refund config and an active mock refund tool through the config loader. |
| Case classification & extraction (`refunds.py`) | Requires `returns_refunds` classification (meeting `auto_confidence`) and validated `order_reference` extraction (`order_number`) for the message | Returns `{"waiting": "refund_intent_required"}` or `{"waiting": "validated_order_required"}` | `wf_case_pipeline` calls `POST /understand` to record classification and extraction for the message. |
| Order identity & current eligibility (`order_money_authorized`, `refunds.py`) | Requires `order_identity_check` (`identity_verified = true`) and `order_refund_eligibility` (`eligible = true`, valid `refundable_amount` & `currency`) as latest executed checks on the `(case, message, order_number)` within SLA/staleness bounds | Returns `{"waiting": "current_eligibility_required"}` or eligibility failure reason (`order_not_found`, `not_delivered`, `window_expired`, `already_refunded`, `invalid_eligibility`); DB enforces via `order_money_authorized` on action insert/update | `wf_lookups_run` executes identity and eligibility checks for the message. The mock eligibility connector reports when the order is already refunded or outside its refund window. |
| Policy safety gates on proposal (`refunds.py`) | Tenant AI budget exceeded (G8) or open case escalation (G1) blocks auto/proposal | Returns `{"waiting": "refund_policy_blocked"}` | For G8, the next monthly budget period or a budget update by the tenant configuration operator permits another evaluation. For G1, the human case operator resolves the escalation before `wf_case_pipeline` calls `POST /decide` again. |
| Eligibility & policy freshness on approval/claim/consume/replace (`enforce_order_money_approval`, `consume_mock_grant`, `replace_unused_mock_grant`) | Revoked eligibility (e.g. a newer failed/ineligible `order_refund_eligibility` execution on `(case, message, order_number)`) or stale policy revision blocks transition to `approved` or mock dispatch (`409 Conflict`) | Action stays in `pending_approval` or `approved` without executing money payout | `wf_lookups_run` records new evidence for the message and `wf_case_pipeline` calls core to decide. If the refund stays blocked, `wf_sla_watchdog` calls `POST /actions/approvals/expire` for a pending request or `POST /actions/approvals/expire-unclaimed` for a resolved approval. If the worker already claimed it, `wf_action_reconciler` calls `POST /actions/{id}/reconcile` after the lease. |
| Edited refund amount/currency refusal (024 + 025 `POST /approvals/{id}/decide`) | `apply_approval_disposition` -> `enforce_order_money_evidence` rejects any `amount` or `currency` differing from eligibility evidence; `/approvals/{id}/decide` maps this to `409 Conflict` | Request remains `pending`, action remains `pending_approval` (or `proposed`), `0` `approval_decisions` written | The reviewer can approve, reject or escalate via `POST /approvals/{id}/decide` or the signed Slack callback. `wf_sla_watchdog` calls `POST /actions/approvals/expire` when the SLA elapses. |
| Mock grant & execution invariants (024) | `consume_mock_grant` requires matching non-expired unused grant, `adapter = 'mock'`, valid `order_money_authorized`, current policy, and an `approval_decisions` row (`approved`). `complete_mock_money` requires consumed unexpired grant and `executed_at` | `claim` / `consume` / `complete` fails closed (`409` or SQL exception) | The same worker calls `POST /actions/{id}/claim` to replace an unused, policy-stale grant within its original lease if core still authorizes it. After the lease, `wf_action_reconciler` calls `POST /actions/{id}/reconcile` with receipt evidence. `found` records `executed`. Confirmed absence after 30 seconds records `failed` and releases the order. |
| Approval SLA expiry & late-decision block (008 + 025) | Before `sla_due_at`, `expire_approval_request` returns `false`. At/after `sla_due_at`, `expire_approval_request` sets `approval_requests.status = 'expired'` and cancels pending/proposed actions (`actions.status = 'cancelled'`) with `action.cancelled` audit event. Late `/approvals/slack` or `/approvals/{id}/decide` calls past SLA or on `'expired'` requests fail closed (`409`) | Expired approval request (`expired`) and cancelled action (`cancelled`) can never be approved, claimed, or consumed | `wf_sla_watchdog` calls `POST /actions/approvals/expire`. The cancelled action releases the order so a new inbound message can verify eligibility and propose a fresh refund. |

## Deployment

Apply migration 025 after 024. Configure `SWITCHBOARD_APPROVAL_CREDENTIALS` if using non-Slack API/web approval decisions via `POST /approvals/{id}/decide`.
