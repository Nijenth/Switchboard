1 · Summary

What we are building, in one page

Businesses want AI to handle support emails, sales leads and supplier invoices. The risk is not that the model writes a poor sentence. The risk is that it refunds the wrong order, emails a customer something untrue, or leaks one customer's data to another. Switchboard is built so those outcomes are refused by the system, not merely discouraged by a prompt.

The idea

  • The model proposes. It classifies, extracts and drafts. Its output is data.
  • The policy engine decides. Fixed safety rules, then the use case's rules, then the customer's stricter rules.
  • A person approves anything involving money or low confidence, in Slack, within a deadline.
  • The database enforces the result and keeps a tamper-evident record.

The shape

  • One generic engine. Each use case is a pack: a folder of configuration.
  • n8n is the hands. Triggers, sequencing, retries, connectors.
  • A small core service is the brain and the ledger. It makes every decision and is the only writer of engine data.
  • Three launch packs: customer support, lead qualification, invoice processing.

2 · Case study

The problem and the approach

What goes wrong with "just add an AI agent"

FailureHow Switchboard prevents it
The model is tricked by text in an email or a PDF All external content is wrapped as untrusted data. An injection flag escalates the case to a person. Nothing the model writes can grant a tool, change a threshold or skip an approval.
The AI issues a refund or payment on its own Every money tool always needs approval by the required role. The database refuses to execute a money action that has no approver.
A reply states something that is not true Outbound text must cite a knowledge passage or a tool result. An uncited draft goes to a person.
Order details are sent to someone who is not the customer Tools that need a verified identity return nothing until identity is verified. The only allowed output is a request to verify.
A crash causes a double refund Each action is claimed by one worker under a lease. An action whose outcome is unknown can never be retried blindly; the system first looks for the effect.
One customer's data appears in another's case Three layers: composite foreign keys, row-level security that returns zero rows without a tenant context, and tenant filters in every query.
Nobody can explain afterwards why something happened Every decision records the rule that fired and a snapshot of its inputs. The audit log is append-only and hash-chained, and is checked against a checkpoint stored outside the database.

A worked example: a refund request

A customer of Northwind Apparel emails to ask for a refund on an order. This is the path the demo runs today, on mock shop data.

  1. 1n8nReceives the email through a signed webhook and posts it to the core service.
  2. 2CoreCreates the case once (a repeated delivery is recognised and ignored), redacts personal data with rules (known gaps: it misses names and addresses outside its patterns), checks for prompt injection.
  3. 3CoreClassifies the message as a refund request and extracts the order number, with a confidence for each field.
  4. 4n8nRuns the read-only lookups core proposes: identity check first, then the order and its refund eligibility.
  5. 5CoreRuns the policy engine. A refund is a money tool, so the decision is needs_approval. A refund action and a reply draft are created as proposals.
  6. 6ManagerSees the request in Slack with the amount, the reason and the draft, and approves it before the deadline. Core verifies the Slack signature and the reviewer's role.
  7. 7n8nClaims the approved action. Core hands out one single-use grant. n8n performs the refund in the mock shop and reports the reference back.
  8. 8LedgerThe decision, approval, execution and reply are in the audit log under one trace ID.

If the reviewer does nothing, the SLA watchdog escalates. If the worker dies between the refund and the report, the reconciler finds the refund by its idempotency key and records the true outcome.

3 · Architecture

The pipeline

Every piece of incoming work, whatever the channel or use case, passes through the same ten stages.

How a decision is made (stage 6)

There are four possible decisions: auto, needs_approval, escalate and ignore. Rules are evaluated in three tiers. A later tier can only make the result stricter. If nothing matches, the answer is needs_approval.

4 · Architecture

Who owns what

Switchboard is an n8n-based platform, not a replacement for n8n. The core service exists only for what a workflow tool should not be trusted with: deciding, authorising and recording.

Database logins: least privilege, enforced by the database

LoginUsed byCanCannot
app_coreCore serviceRead configuration; read, insert and update operational tables; insert audit entriesChange packs, tools or approval roles; edit or delete audit; delete anything
app_config_loaderPack loaderWrite packs, tools, tenant configuration, knowledge, eval casesTouch cases, messages, actions, approvals
app_n8n_mockn8n mock toolsRead and write the demo schemaRead any engine table
app_reportingDashboardsRead reporting viewsRead raw tables

The consequence: the AI path cannot change its own permissions. Which tools exist, how risky they are and who must approve them change only through Git, CI and the pack loader.

5 · Architecture

Executing an action exactly once

The hardest part of letting software act is the moment between "the refund was sent" and "we recorded that the refund was sent". The protocol below makes a crash in that gap safe.

  1. 1Core/decide creates action rows as proposed or pending_approval. Nothing else can create an action.
  2. 2ReviewerApproves in Slack. Core checks the Slack signature, the reviewer's role, the deadline and that the approved content is exactly what was shown.
  3. 3n8nCalls /actions/{id}/claim. Core atomically sets the action to executing with a worker ID and a lease. Only one claimer can win. It returns a single-use execution grant.
  4. 4n8nConsumes the grant to receive the approved payload from core, then calls the external system, passing the action's idempotency key.
  5. 5n8nCalls /actions/{id}/complete with the external reference. Core records executed or failed.
  6. 6ReconcilerIf the worker crashes between 4 and 5, the lease expires and the action becomes unknown_outcome. The reconciler looks the effect up in the external system and records what it finds.
The rule that matters most: an action in unknown_outcome can never be retried blindly. This is enforced in the database, not just in application code.

Tool risk levels

LevelMeaningWhen it may run
readLooks data up, changes nothingWithout approval
writeCreates or updates recordsOnly if the decision is auto and a pack rule allows the tool
external_commSends something outside the companyOnly with a draft authorised for that exact text
moneyRefunds, payments, discountsAlways needs an approver in the required role

Release gate 3: where the real credentials live

Before any real connector runs, the grant must be enforced in the place that holds the provider credentials. If n8n held the Shopify and Gmail credentials, the grant check would be a convention inside a workflow, and an edited workflow could refund an order without one. The owner chose a separate connector gateway (ADR 0032):

  • n8n sends the gateway only an action ID. The gateway claims and consumes the grant itself, so the approved payload comes from core and never from n8n.
  • It refuses unless the grant is for the real adapter, the tool has a registered connector, it holds a credential for that tenant and destination, and enough of the lease remains.
  • It searches the provider for an earlier effect of the same idempotency key, and writes once only if none exists. A write whose result is unclear is never retried and never marked complete.

Real dispatch is off  Core answers "refused" for the real adapter and the database functions accept only the mock adapter. Nothing real can execute, even with credentials configured. Turning it on needs its own reviewed migration.

6 · Blueprint

Packs: a use case is a folder

Adding a use case means adding a pack, not changing the engine. A pack is versioned. Changing anything means a new version, and each tenant pins the version it runs. CI fails if a pack does not validate.

packs/<pack_key>/
  pack.yaml        identity, channels, intents,
                   confidence thresholds
  schemas/*.json   what to extract, and the
                   shape of outputs
  tools.yaml       tools this pack may use and
                   who must approve them
  rules.yaml       business rules, as data
  prompts/*.md     versioned prompts
  knowledge/*.md   policies, FAQs, price lists
  evals/cases.jsonl  golden test cases
  README.md        what it does, demo script
- id: INV_NO_PO
  when: { field: checks.po_found,
          op: eq, value: false }
  then: { decision: needs_approval,
          role: finance,
          reason: "No matching purchase order" }

- id: INV_CLEAN_MATCH
  when:
    all:
      - { field: checks.po_found,
          op: eq, value: true }
      - { field: checks.po_variance_pct,
          op: lte, value: 2 }
  then: { decision: auto,
          allow_tools:
            [invoice_post_to_accounting] }

Rules are data, evaluated by a small safe condition language (all, any, not, and comparisons on named fields). Rule content is never executed as code. Among matching pack rules, escalate outranks needs_approval, which outranks auto. Missing data can only make the result stricter.

Release gates that block a merge

  • Intent accuracy of at least 90% per pack.
  • Exact match of at least 95% on required invoice fields.
  • Zero auto decisions on eval cases tagged must-escalate, injection or money.
  • Zero tool data leaked on eval cases tagged unverified.
  • All failure-mode tests pass before Pack 2 begins: two workers claiming one action; a worker killed between the external call and completion; an external timeout; a duplicate webhook; an approval arriving after its deadline; a missing tenant context; a mock grant sent to a real branch.

How the work is controlled

  • Work is delivered as stacked branches with a review queue: what changed, how to test it, what was verified and what was not. The owner reviews, tests and merges. Builders never push to or merge into main.
  • Every claim is labelled as observed, inferred, unverified or reported by others.
  • A database constraint that blocks the code is never weakened to make the code work.
  • Every lock, lease, pending state and limit must have a documented way out.

Not verified

  • Any real provider. No request has been sent to Shopify, Google or a paid model.
  • Hosted CI for the three newest branches, and independent review of the latest fixes.
  • The gateway against the real core service. It is tested against a stub.
  • Live schedules, queue-mode workers and the audit checkpoint schedule in a deployment.
  • Real-model accuracy, cost and latency.

Known limits

  • A PostgreSQL superuser or table owner can bypass triggers and row-level security. Running services use restricted logins, and the audit checkpoint must be protected under a separate identity.
  • External systems without idempotency keys can still duplicate on a crash; the reconciler must search before creating.
  • An n8n call to core timed out intermittently at 5 seconds under load. The cause is not established.
  • The gateway measures the lease against its own clock, with an 8-second margin.
  • Core's dispatch does not yet carry the email thread fields a real Gmail reply needs.

What comes next

  1. Owner review and merge of the live demo stack, the console and the connector gateway.
  2. A separately reviewed migration that enables real dispatch, including the claim design and the reply thread fields. Then a Shopify development store and a test Gmail mailbox, with recorded fixtures replacing the synthetic ones.
  3. Pack 3 (invoices) and Pack 2 (sales leads), each on mock data first.
  4. Phase 6: dashboards, budgets, the injection suite and the demo deployment.
